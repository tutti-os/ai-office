# PDF Export Plan

## Context

AI Doc needs a PDF export/download capability. The product runs as a Tutti workspace app in production, while local debug server mode can run without the Tutti desktop host.

The current document export flow is:

- HTML and Markdown exports are produced in the web app and saved through `POST /api/projects/:projectId/exports`.
- DOCX exports use browser-side `@tutti-os/office-export` and then save the generated bytes through the same server export endpoint.
- Export files are stored under each project workspace `exports/` directory.

PDF export should not be added to `@tutti-os/office-export`. That package remains focused on browser-side Office export.

## Decision

Use the Tutti Electron host as the primary PDF renderer.

The intended production flow is:

1. AI Doc prepares the current document HTML.
2. AI Doc calls a narrow Tutti host PDF capability.
3. Tutti creates hidden Electron rendering contents.
4. Tutti calls Electron `webContents.printToPDF()`.
5. Tutti returns PDF bytes to AI Doc.
6. AI Doc saves the bytes through its existing project export endpoint.

This avoids shipping or downloading a second Chromium for PDF export. Tutti already ships Electron, and Electron already contains the Chromium engine needed for print-to-PDF.

## Non-Goals

- Do not depend on global `officecli`.
- Do not depend on global `playwright`.
- Do not depend on global Chrome, Chromium, Edge, or Playwright browser caches.
- Do not add Playwright or Chromium as the default PDF path.
- Do not download Chromium for normal Tutti production PDF export.
- Do not make standalone debug server PDF export a requirement for the first version.

## Why Not Playwright First

`playwright-core` alone is not enough for PDF export. It is only the browser controller. The actual `page.pdf()` flow still needs a compatible browser executable.

Current npm size notes:

- `playwright-core@1.61.0` tarball: about 2.86 MB.
- `playwright-core@1.61.0` unpacked: about 12.7 MB.
- It does not include Chromium.

Playwright can remain a future fallback, but the primary production path should be Tutti Electron `printToPDF()`.

## Tutti Work

Add a host PDF capability to Tutti desktop.

Required behavior:

- Accept HTML and print options from a workspace app.
- Render in an isolated hidden Electron context.
- Wait until the document is loaded and ready for print.
- Call `webContents.printToPDF()`.
- Return PDF bytes to the caller.
- Clean up hidden windows/webContents after success or failure.

Likely bridge shape:

```ts
window.tuttiExternal?.pdf?.printHtmlToPdf({
  html,
  title,
  printBackground: true,
  pageSize: "A4",
  margin: {
    top: "12mm",
    right: "12mm",
    bottom: "12mm",
    left: "12mm",
  },
});
```

Exact DTOs should be defined in Tutti where workspace app bridge contracts live.

## AI Doc Work

Add PDF export in the document app.

Tasks:

1. Add `application/pdf` to supported project export MIME types.
2. Add `.pdf` filename normalization on the server.
3. Add a PDF item to the HTML editor export menu.
4. Add a PDF item to the Markdown editor export menu if Markdown can provide print-ready HTML.
5. Call the Tutti PDF bridge when available.
6. Save returned bytes through `writeProjectExport`.
7. Disable PDF export or show a clear local-only error when the Tutti bridge is unavailable.

Initial debug behavior:

- Standalone debug server mode does not need PDF export.
- When the Tutti bridge is missing, the UI should not try to download Chromium.
- A future dev-only fallback can be added behind an explicit env flag if needed.

## OfficeCLI Toolchain Change

OfficeCLI should follow the same managed-toolchain rule.

Current behavior probes global `PATH` with `officecli`. That should be removed from normal flow.

Allowed sources:

- Explicit development override, such as `AI_DOC_OFFICECLI_PATH`.
- Future Tutti-managed injection, if provided.
- App-managed install under app data, such as `AI_DOC_HOME/toolchains/officecli`.

Disallowed normal source:

- Global `officecli` from `PATH`.

The existing detect/download/status UX can remain, but it must not silently use a globally installed version.

## Implementation Status

Implemented:

- Tutti desktop exposes `pdf.printHtmlToPdf()` on `window.tuttiExternal`.
- Tutti validates the PDF print DTO in `@tutti-os/workspace-external-core`.
- Tutti renders print HTML in a hidden Electron `BrowserWindow` and calls `webContents.printToPDF()`.
- AI Doc accepts `application/pdf` exports and normalizes `.pdf` export filenames.
- AI Doc HTML and Markdown screens have PDF export menu items.
- AI Doc saves returned PDF bytes through the existing project export endpoint.
- Standalone debug server mode disables PDF export when the Tutti bridge is unavailable.
- OfficeCLI normal flow no longer probes global `officecli` from `PATH`.
- Export UI now has disabled/loading states, clear bridge-missing error copy, and a visible success confirmation.

Settled answers:

- The Tutti bridge returns PDF bytes as `Uint8Array`.
- AI Doc passes print-ready HTML, not a print route URL.
- Default PDF output uses A4, background printing, and 12 mm margins with a 14 mm bottom margin.
- AI Doc rewrites project asset references to absolute local app URLs before PDF export.

## Open Questions

- Should print CSS be added to AI Doc HTML documents before calling the host?
- Should the Tutti host capability be web-bridge only, app-server callable, or both?

## Suggested Implementation Order

1. Add Tutti host `printHtmlToPdf` capability and a tiny internal smoke test.
2. Add AI Doc PDF MIME support in the export endpoint.
3. Add AI Doc web bridge wrapper with feature detection.
4. Add HTML document PDF export.
5. Add Markdown PDF export after settling Markdown-to-print-HTML conversion.
6. Remove normal global `officecli` PATH probing.
7. Add product polish: disabled state, error copy, loading state, and export confirmation.
